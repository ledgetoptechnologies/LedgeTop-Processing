# Draft: preserve uploads and task directories on submission conflicts

This draft applies to the exact NodeODX/NodeODM images in the accompanying startup-preservation draft. It refuses a pre-existing task destination before initialization, before a commit removes its upload metadata, and before a legacy one-shot upload. It also checks again before task creation and uses a non-destructive destination check inside asynchronous initialization. A retry cannot overwrite an already-existing temporary upload directory or its `body.json`. Error and asynchronous initialization-failure paths retain upload and destination files for reconciliation instead of automatically removing them.

The actual engine API returns its existing JSON error format; this draft does not add an HTTP 409 status. A repeated or lost-acknowledgement request can therefore require operator reconciliation, and retained temporary files need later accounted cleanup. An asynchronous failure can still be acknowledged with a UUID before the failure is known.

`tests/nodeodm_submission_preservation.js` starts the actual engine HTTP app in built-in test mode inside an isolated, network-none disposable container using tmpfs for all synthetic task/upload data. It tests existing destination at init and commit, repeated init after an acknowledgement, an asynchronous initialization error after uploading two tiny files, and a commit connection intentionally closed before reading its response followed by a retry. It verifies the original or uploaded files are retained. These tests do not process genuine photos, test power loss, or establish crash-safe submission/index durability.

This is **not production-ready**: the engine still acknowledges before asynchronous initialization and index persistence, has no durable submission-intent journal or verified upload quiescence, and a faulted index writer cannot yet drain/reject already-in-flight requests. A task may remain held after a crash and requires safe reconciliation. The checks are not an authority fence against concurrent direct clients or host administrators. No production container, credentials, data or NAS settings should be altered from this draft.
