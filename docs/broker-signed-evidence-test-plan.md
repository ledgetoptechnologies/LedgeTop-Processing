# Signed broker evidence — inactive candidate and interruption test plan

This candidate records the exact canonical public grant and signature in the coordinator transaction that creates a started broker intent, and in the node transaction that records the started operation. A successfully received and validated synthetic engine response is recorded separately before the authority recheck. The response is an observation only: it does not mark the operation or coordinator intent complete, clear NodeGate, authorize a retry, or establish who could access the engine. If the response was lost before receipt, no observation is recorded and the outcome remains unknown.

This is not an all-node recovery/release protocol. It does not prove a real NodeODM identity or receipt, authenticate a node to a new coordinator epoch, fence an external writer or Docker administrator, provide an adoption route, or migrate existing broker/intent schemas. Existing installations without these exact new schemas fail closed. The append-only triggers reject ordinary updates/deletes and duplicate `INSERT OR REPLACE`, with recursive triggers both on and off. They are not a boundary against arbitrary SQLite writers, trigger removal or schema replacement. The evidence verifier independently checks the MAC over canonical bytes with the correct trusted signing key; hexadecimal formatting alone is not authentication. Key storage, rotation, access control and historic-key availability remain deployment prerequisites. Public grants can include filenames and task identity; keep evidence private and do not print it to logs or review notes. Claim tokens and signing keys are not intentionally persisted in these evidence rows.

## Proposed owned interruption test — independent review required

No process signals, Docker containers, volumes, snapshots or certificates have been created for this candidate. Before any such action, independently review the exact code, schemas, trigger coverage, signal ownership, watchdog, synthetic inputs and resource retention. Reuse the owned-isolation topology and Windows Job Object procedure in the separately reviewed `synthetic-remote-outage` rehearsal, with a fresh immutable snapshot of the reviewed candidate commit and fresh synthetic-only certificates. Keep all resource names, full IDs and per-run labels; do not use customer data or production paths, and do not delete resources.

A synthetic engine should fsync its forwarding marker and pause its response. After observing that marker, verify the exact owned coordinator full container ID/name/label and running state, KILL only that ID, verify it exited, and release the engine response. The broker must record the received bounded response observation but keep the node operation started and the NodeGate reservation held when the mTLS authority recheck fails. An exact same-session retry must fail before another engine request. A distinct verifier should acquire the coordinator authority lease before reopening the synthetic Queue, and check: coordinator intent remains started; coordinator grant evidence has the original operation ID, exact canonical grant bytes and signature; node grant evidence matches; node response observation has the original grant digest and synthetic task UUID; job remains held; and the engine recorded one request. Failure to prove any binding is INCONCLUSIVE, not permission to release.

Separately exercise a response lost before the node caller receives it. That case must leave no engine observation, retain started intent and reservation, and refuse replay; absence of an observation is not proof the engine did not perform the operation. If adding tests that terminate processes or containers, stage exact owner checks and signal targets for independent review before execution. The watchdog must verify all owned containers stopped and retained, record exact IDs/labels and Job Object process counts, and report late-create or descendant uncertainty. No recursive cleanup or shared-resource changes.

## Coordinator-side restart inspection

The inactive `inspect_coordinator_held_grant` helper pins the exact local Queue lifetime and installed authority lease, checks the authority marker and broker-intent fence in a read transaction, verifies the persisted canonical grant's HMAC using a separately supplied trusted key, and ties the old epoch, started intent, held job, node, task generation and claim hash to the new coordinator state. It returns `authorizesRelease=false`, `nodeState=unverified`, and `engineState=unverified`. The result may contain private grant details such as filenames; callers must enforce access controls and must not log it.

This helper does not acquire a node gate, inspect the node's journal or engine, establish physical exclusivity, obtain independent node attestation, or authorize reconciliation. Its timeout bounds lease/pin acquisition only; SQLite, filesystem and mutex operations are not guaranteed to end by the deadline. It is not a recovery API or a production listener. Missing/rotated keys, missing or changed schemas, incomplete evidence or an unqualified runtime must remain held. All-node sessions, cross-epoch node proof, engine provenance, migration and release remain separate work.

## Node-local and coordinator evidence match — inactive

`NodeMutationBroker.inspect_held_evidence` examines the old-epoch broker's own started init, exact signed grant, optional engine response observation, reservation and node journal while holding its local NodeGate and mutex. It checks the local Docker engine/backend identities before and after the read. It signs a nonce-bound report using the shared synthetic broker key. `match_coordinator_node_evidence` verifies that report MAC and exact signed grant against a fresh `inspect_coordinator_held_grant` call under the restarted coordinator lease. It only reports a match: `authorizesRelease=false`, `engineTaskState=unverified`, and `nodeIdentity=not-independently-authenticated`.

These are point-in-time in-process diagnostics, not an authenticated remote API or continuing cross-host fence. A shared-key holder can construct a report, so the MAC is not an independent device identity. The local engine probes and held gate are cooperative, do not exclude host/Docker administrators or another process using a direct engine endpoint, and are not a query of actual engine task state. The engine response observation is not proof of provenance or completion. Missing observation remains unknown. The caller must generate a cryptographically fresh nonce, supply the trusted historical key securely and avoid logging sensitive grant/response fields. Timeout bounds are partial, not a guarantee on all filesystem, SQLite or mutex operations. No reconciliation, replay, epoch adoption or release is implemented.
