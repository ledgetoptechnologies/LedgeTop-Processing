# Actual broker + isolated synthetic engine rehearsal — review draft

Status: plan only; no new Docker resources, source snapshots, certificates, or processes have been created. The previous namespace rehearsal used run `cfec178134bef531303e80e0`; its stopped resources are retained and must not be reused or modified by this test.

## Purpose and explicit limits

Exercise the real `NodeMutationBroker.mutate` and `LoopbackNodeODM.exchange` code against a synthetic NodeODM-compatible HTTP service inside a loopback-only Docker network namespace. Use a separate, authenticated control channel from an independent coordinator/probe container. Verify a signed synthetic init reaches the synthetic engine exactly once, and an unauthenticated client and separately isolated probe cannot invoke it through the test control path.

This is a test harness, not a production listener or a qualified two-node authority protocol. The actual broker's engine and backend identity probes expect the local Docker daemon and a Docker-published loopback port. The engine in this topology has neither a published port nor a mounted Docker socket. The harness must replace **only those two probes** with deterministic synthetic identity fixtures, and explicitly assert that they were replaced. It must not set or claim any physical-fence qualification. An open Docker socket would let its holder attach containers, reconfigure networks, and bypass the boundary; do not mount it into any test container. The existing broker qualification flag is false and may be overridden **only in the isolated synthetic process**. No changes to installed code, configuration, real NodeODM, or production PCs.

The production engine identity problem and node-exclusive ownership remain unsolved. Host root, Docker administrators and anyone who can join the network namespace or access the shared control socket can interfere; TLS authenticates a peer but does not constrain a malicious administrator. Point-in-time census or a successful init does not enable safe recovery release, authorize processing, or prove upload/commit/results.

## Owned resources and reproducibility

Before execution, pin the source to an independently reviewed commit in the `node-broker-remote-durable` branch and record the full Git commit and tree IDs. Stage a minimal, task-owned **read-only** source snapshot containing the required Processing Python package and the harness, rather than mounting the full worktree, user data, `.git`, SSH credentials, or Docker socket. Stage only synthetic key pairs/certificates, a synthetic job/input and immutable local image IDs. Keep source snapshot, synthetic certificates, stopped containers, named volumes and test logs for inspection; no recursive cleanup or resource deletion. If a source snapshot or test harness requires generated files, use a unique per-run directory, record its absolute path, and do not alter user-owned files. Confirm a local immutable Python image is available; do not pull a floating tag.

The four containers are: (1) broker plus namespace-holder, (2) synthetic engine sharing the broker's exact network namespace, (3) separate coordinator/control client, and (4) unauthorized probe. Use per-run random names and label, non-root where possible, read-only root filesystems, no added capabilities, no host networking, no published ports, no restart policy, small CPU/memory/pid limits, and no Docker socket. A task-owned named volume may hold the synthetic broker's state and a second task-owned named volume may carry its Unix-domain control socket. Mount the control volume only where required; do not mount broker state into the coordinator/probe. An unauthorized control probe can optionally receive the control socket mount but **not** the authorized client's private key, demonstrating certificate authentication rather than assuming filesystem separation.

Unix socket directory permissions and Docker Desktop named-volume ownership must be demonstrated by the test, not assumed. The control client may use TLS over the Unix stream directly only if the standard library TLS wrapper accepts the exact socket types; otherwise stop and review a separate byte-preserving relay. Do not silently replace mTLS with a shared unauthenticated local socket. Keep the actual broker's `LocalCoordinatorAuthority` with a real synthetic Queue and lease in the broker process for this first test; the coordinator client submits the existing signed grant through a test-only mTLS handler. This does not exercise the current remote `RemoteAuthoritySession` or bind an independent coordinator's lifetime.

## Proposed test and observations

1. Independently review the exact source commit, harness, watchdog, resource ownership and shutdown behavior before any creation, start or stop. Reuse the reviewed Windows Job Object watchdog pattern. Record and reconcile every exact full container/volume ID, exact name and per-run label, including uncertain timeout outcomes; stop only independently verified owned containers. No deletion. Wait/reap all owned processes and report any unverified descendants or possible late Docker creates.
2. Broker namespace has `network=none`; engine uses `network=container:<broker full ID>` and listens only on an unprivileged IPv4 loopback port with a unique marker. Inspect actual namespace identities and `/proc/net/tcp{,6}` and verify no Docker-published port. Coordinator and probe have distinct network namespaces and cannot route to the engine namespace. Distinguish host Windows/Docker Desktop VM from container namespace.
3. Harness creates a real synthetic Queue, `AuthorityLease`, `TaskStore` and broker reservation and uses the actual `issue_init_grant` / `mutate` path. It writes the authorized TLS client key only to a run-owned path available to the coordinator and writes the server credentials only to the broker. TLS server and client must each validate certificate chain **and** exact configured certificate pin. The test control request is narrowly framed and bounded in size and time; the harness must never offer arbitrary shell, Docker or engine access.
4. Authorized coordinator submits one signed init over the control socket. The synthetic engine records request count and task UUID using only synthetic state. Assert the actual NodeMutationBroker returns matching success and its persistent operation journal says `complete`. Replay the same grant and assert identical response and still exactly one engine request.
5. Independently exercise a client with missing/wrong certificate, a mismatched pin or malformed request; assert no engine request or mutation occurs. A separate probe without the socket volume checks only its own isolation; lack of the mount is not proof that a mounted but unauthorized client is blocked. Record filesystem and TLS outcomes separately.
6. Inspect exact IDs, labels, namespaces, socket visibility and published-port settings again. Stop and verify all owned containers using reviewed watchdog rules; retain the named volumes, bridge if any, and all stopped resources. Any timeout, unknown identity, background process, malformed observation, control-channel setup failure, missing permission or incomplete cleanup makes the whole run inconclusive. No PASS until process and resource states are verified.
