# Driver fetched-input accounting

`ReferenceDriver(..., input_copy_accounting=True)` connects real fetched bytes to the optional scratch input-copy ledger. The trusted composition must first construct `ScratchLedger(..., input_copy_accounting=True)` and explicitly call `enable_input_copy_accounting()`. The driver never enables the ledger, invents source receipts, releases input copies, invokes input cleanup, or removes native tasks.

The default driver flag is `False`. Its persisted binding and legacy fetch path remain unchanged. A marked/opted-in ledger with a default driver, a non-boolean flag, or a changed live driver/ledger profile refuses. The enabled driver adds an `inputCopyAccounting` version to its own durable binding. It cannot adopt a previously bound legacy driver journal, even if empty, or an unbound journal containing old jobs. Enabling a daemon/configuration and any deliberate historical migration require separate review; this change supplies neither.

After reserving scratch, the enabled driver derives the full closure from the original manifest and persists a registration intent before registering any row. The paths are exactly `jobs/<reservation>/<objectId>.input`. The ledger binding includes the original job, generation, production/staging environment, input manifest, pipeline digest and closure digest. A crash after registration but before its return can replay only that same persisted intent. A committed binding missing from the ledger is held, never silently recreated during fetching.

Fetching still advances **one object per driver step**, preserving control/gate responsiveness. The enabled profile keeps a bounded process-local cursor over the original manifest order, with a durable prefix count and byte counter. At cold entry it reconciles the ledger's actual closure and the journal's exact prefix, checks fetched/cleaned metadata, and rehashes recovered prefix files once. A count alone never selects or attests an input, and a journal-provided path never becomes the verification path. Every new download, or target published before a crash, passes the actual worker `_file` size/hash/regular-single-link verification before `confirm_input_copy`. An existing unconfirmed target without the driver's durable download attempt is refused.

The ordering is download attempt → broker publication → actual byte verification → ledger confirmation → monotonic allocation → journal prefix. Crashes between those boundaries retain the file and replay verification/confirmation without repeating a successful download. If journal commit completed before its return was lost, a fresh driver reconciles that committed prefix; the old process cursor cannot silently skip to a changed count. Full closure and prefix checks run again before the processing transition, and the original claim/closure is checked before first engine execution. The engine adapter verifies actual input files at its start boundary. A hot older-prefix journal path change is caught at the final prefix check; it is never used as a download or confirmation path.

This is the first bookkeeping integration, **not 10,000-photo throughput readiness**. The added bookkeeping uses a constant-size per-object lookup/confirmation and incremental byte counter, with full closure work at registration, cold-session reconciliation and phase/execution boundaries. It does not add a full-closure rescan or manifest-wide byte SUM for every object. Existing driver behavior still parses and serializes the full claim and growing `inputPaths`, and validates the full grant/manifest, on each step. That pre-existing quadratic metadata cost remains. The 10,000-object test isolates new bookkeeping, skips full JSON journal writes in that test only, and creates 10,000 tiny synthetic files using the actual driver helper, ledger, broker and file verifier. It proves bookkeeping call counts and retention, not 50 GB transfer performance.

Before large-batch qualification, a separate indexed journal design must persist immutable validated manifest rows and exact profile/closure identity once, fence changes to that immutable claim, keep per-object attempts/progress in indexed rows, and provide a one-object fast path with bounded reads. Cold recovery must still revalidate durable identity and actual bytes. That design must include a deliberate journal ABI/downgrade fence and private storage-cap qualification; no current quota is enlarged here.

Success and failure leave input copies on disk. No configured `InputReleaseAuthority` is created. Actual authenticated source custody, purge-path pins, whole-parent finality, release acknowledgement and a reviewed cleanup consumer remain prerequisites for eventual automatic reclamation.
