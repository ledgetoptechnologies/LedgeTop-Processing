# Claim-bound Viewer input transfer prototype

This disabled, Linux-only prototype does not dispatch an engine, acknowledge input custody, release a reservation, or delete data. It is not qualified for client data. A worker replays its authenticated coordinator claim, verifies the local gate and output allocation, freezes the paged inventory and checks its digest, then allocates and verifies each input independently. The local input journal records intent before allocation and holds partial or ambiguous operations for inspection after interruption. Replayed inventory and input bytes are revalidated; retained files are never automatically removed.

The source endpoint authenticates a worker principal and claim token and binds each request to a claimed object and frozen source identity. An authenticated worker now submits its locally committed gate and slot identity to the coordinator, which persists an immutable claim-bound acknowledgement before serving inventory or bytes. This is a **self-reported attestation by a trusted worker**, not remote cryptographic proof of its physical reservation or continuing availability; the local implementation rechecks its gate and slot before operations, but a privileged or noncooperative node could lie or bypass those checks. The endpoint remains disabled pending independent review and integration testing. The configured mapping between gate origin and verified TLS origin is trusted provisioning, not remotely proven by this code.

The source checks its file identity and digest while streaming, but HTTP status and bytes already sent cannot be retracted after a late error. The receiving worker independently verifies the complete length and hash before recording an input verified; incomplete transfers remain held. The hash compares against upload-time metadata and is not independent authentication of the original source. Source stream concurrency is limited to two per coordinator service instance, not across processes; HTTP request threads are not globally limited by this prototype.

Authorization is checked when a stream is opened, outside the subsequent streaming lifetime. A later claim, receipt, or job state change does not revoke an already-open stream; this is not a remote live lease. Future gate design must explicitly define and test in-flight authorization revocation or accept and document that limitation.

Transfer reads are bounded to 1 MiB at a time, with a 30-second inventory request deadline and a one-hour per-object deadline. The initial claim, inventory verification and process-restart revalidation inspect all metadata; individual downloads are sequential. Capacity is allocated per input as it is downloaded, not reserved for the complete dataset in advance. Exhaustion or a mismatch leaves existing data and reservations held. The caller must provision and verify input root, mount, and size limits. Filesystem preallocation does not guarantee physical capacity on thin-provisioned or failing storage. The journal's locally stored MAC key detects accidental corruption but does not protect against a hostile process with the same OS identity.

The input metadata database is capped at 64 MiB even though the protocol permits up to 100,000 entries; the prototype does not establish that every protocol-sized inventory fits. Metadata processing is O(N), and the only 10,000-entry test covers coordinator metadata rather than full transfers. Downloads use complete GET requests with no range resume: an interrupted transfer is held for inspection, not resumed. The watchdog bounds supported network operations but cannot guarantee a deadline for DNS resolution or an uninterruptible filesystem operation.

The experimental authenticated plan endpoint freezes ordered options and outputs in the claim transaction, limits canonical plan bytes to 64 KiB, and checks the claim digest on both coordinator and worker. Worker replay requires a fresh authenticated coordinator response and exact local persisted plan; offline replay holds. The plan contains no dispatch authority. Older prototype databases without the new plan schema fail closed; no migration has been implemented. Initialization and upload acknowledgements remain ambiguous on interruption and must hold rather than be blindly retried.

The new 64 KiB limit applies to the entire wrapped canonical plan object. The earlier validation limited the combined serialized options and outputs without that wrapper, so a previously valid task near the limit can now be held at claim time. No compatibility migration or alternate handling has been qualified.

An isolated multipart transport seam can stream from an already-held input allocation descriptor using the NativeEngine route while checking its recorded identity and byte hash. It is not connected to the worker runtime: it does not acquire the gate, verify that every input is ready, establish an initialized engine task, or persist upload intent and acknowledgement. It therefore does not prevent retries by a caller and must not be used as dispatch authority. A safe runtime must durably journal intent before sending and hold ambiguous results, and retain the actual node gate and input lock throughout. Hash checks cannot retract bytes already sent, and a noncooperative same-UID process may still change the file. The synthetic loopback tests do not establish real NodeODM behavior or test engine execution.

The transport holds its slot's cooperative operation lock for the complete send and acknowledgement. Its 120-second socket timeout is an idle timeout, not a total deadline; DNS or repeated progress can extend the operation indefinitely. The calling runtime needs a separately tested total-deadline and interruption policy before use.

Acknowledgement parsing requires exactly one bounded Content-Length and complete body at that HTTP message boundary; it does not prove physical socket EOF or rule out bytes outside that framed message. Duplicate JSON keys, nonfinite constants and floating-point overflow are rejected at any nesting depth.

Separate strict initialization and commit transport functions reproduce the current NativeEngine request routes and require, respectively, the assigned UUID and an explicit success response. They do not change the legacy engine client. Their response assumptions have only been checked against a synthetic loopback server, not an actual NodeODM version; a real server using chunked responses or a different successful commit shape will hold. The transports do not themselves persist intent or authorize engine calls. No production dispatch is enabled, and enrollment is explicitly `enrolled_no_dispatch`. Socket timeouts are idle limits, not total deadlines.

The synthetic grant returns the task name frozen with the claim, and the synthetic submission path checks its digest and sends the exact name.

The disabled grant prototype requires a running claim and authenticated enrollment; the node verifies its gate, output slot, full inventory, plan and each retained input before requesting a claim-bound `synthetic_execution_grant`. The coordinator records the exact self-reported evidence and immutable response transactionally. A worker can lie; the coordinator cannot remotely prove physical file bytes or continued gate ownership. Input files are checked sequentially and their individual locks released after each check, so this is not a simultaneous snapshot. A stored grant is not a live lease or authorization to bypass a later held job. Prototype schema changes fail closed on old databases and have no migration. Grant verification performs O(N) file reads, including a complete hash of each input; 10,000 real files and 50 GB have not been qualified.

The immutable claim binds a canonical task-name digest; the coordinator and worker independently compare the grant name to that digest. This detects an altered stored name against the existing trusted claim; it does not authenticate the database against privileged modification. Claims created before this digest was added require migration or inspection and cannot be replayed as though they contained it.

An isolated, explicitly opted-in submission experiment connects the synthetic grant to loopback-only HTTP engine calls and journals each initialization, upload and commit intent before sending. A pending mutation after interruption holds rather than resending, and no files or gate reservations are cleaned up. It holds the cooperative local gate and per-input inode lock during the relevant mutation. This is not a qualified deployment: loopback is not proof an engine is synthetic, there is no authenticated engine ingress fence or remote live lease, the database assumes a trusted local OS identity, no result-custody workflow is wired, and tests do not establish real NodeODM compatibility or power-loss durability. It is not connected to production worker startup.

The synthetic worker now obtains a durable, claim-authenticated permit before each mutation and finishes it only after a strict acknowledgement. A cooperative hold request first closes permit admission; if a permit is active it returns `draining`, then changes the job to held after that permit finishes. An already-permitted operation may still begin or finish while draining. A database trigger rejects a running job's status transition while a permit is active; unresolved permits never expire on a clock. A network failure, crash or lost acknowledgement can leave a permit active indefinitely. Coordinator restart then fails closed and remains unavailable until an independently designed reconciliation procedure resolves it; there is no such procedure here.

This is not a physical execution fence. Existing legacy hold and cancellation routes do not use the new drain protocol and may fail or leave partial held state while a permit is active. The worker itself can lie about finishing, a noncooperative caller can reach an exposed engine directly, and no ingress filter verifies permits or their operation sequence. The new hold endpoint is limited to the authenticated worker prototype; no operator-facing cancel flow or production integration exists. Privileged database or host changes are outside this cooperative protocol. None of these guarantees should be used to declare a live node safe for maintenance.

The separate synthetic local-result adapter checks committed local submission and the same gate/binding, polls the exact loopback task UUID for a successful status, and captures the declared-length ZIP into the reserved inode with a durable seal. It then persists an immutable local result intent. It can replay that intent after a worker process restart without coordinator access, and retains the input, engine result and output slot. An explicit retry call can register that metadata with the coordinator and persist the exact metadata-only receipt locally. There is no automatic retry driver. Neither intent nor metadata receipt completes the Viewer job, replicates bytes, proves Viewer acceptance, authorizes deletion, or recovers an interrupted capture. Standard node enrollment still holds when a capture journal exists; the dedicated sealed-result recovery entry point must be used. The ZIP hash is computed locally rather than authenticated by NodeODM, and ZIP checks cover its central directory, not every file's semantics. No source timeout is a complete wall-clock deadline, and local same-identity processes remain trusted.

The seal and local result intent do not independently prove that the engine reported status 40 or that the source was authentic: the generic capture API can create a matching seal without that status observation, and the status response itself is not cryptographically bound to the bytes. The recovery path verifies the retained bytes and local bindings, not the provenance of the earlier observation.

The existing ReferenceSender/DeliveryReceiver cannot provide this Viewer handoff directly: its ReferenceStore accepts the reference-pipeline profile and reference claim/manifest, whereas this task uses the Viewer profile and claim. Its metadata receipt is not Viewer file custody. The Viewer-specific metadata endpoint authenticates the worker and binds its self-reported local record to the claim, grant, output identity and completed commit permit. It cannot verify local bytes, engine completion or source authenticity; it records metadata only and leaves the job's status unchanged. Archive byte custody and exact Viewer acceptance acknowledgement remain to be designed and tested before cleanup or client use. A gate change after the coordinator commits can leave a remote metadata receipt with no local receipt; retry revalidates the local gate and sealed data before recording the same receipt.

The opt-in synthetic archive path now authenticates and checks claim, metadata, exact length and configured spool policy before reading an HTTPS request body. It allocates a separate explicitly provisioned coordinator inode, durably records intent, streams bounded chunks, syncs and independently hashes the stored bytes, then records a coordinator archive receipt. A node holds its sealed reader, checks authenticated spool status before sending, and replays a verified receipt after a lost response; incomplete allocation or transfer remains held without deletion. This proves only that this configured spool reported retaining bytes matching the worker's self-reported metadata, not Viewer acceptance or original source authenticity. It does not change job completion or authorize cleanup.

The spool root, mount identity and per-archive ceiling require trusted provisioning; no deployed configuration or migration exists. An explicit schema-4 reference configuration supplies those values and requires Viewer claims, but the archive schema qualification constant remains false by default. The current schema-4 form cannot also configure the separate recovery or staged-ack settings. The assembled dynamic/control listener delegates archive requests only when the separately bound spool is provided; otherwise the route is closed. Allocation is per archive and does not establish an aggregate quota, resilience to thin provisioning, disk failure or independent backup. Uploads and receipt lookups share a two-operation limit per spool instance, not a global process or HTTP connection/thread limit; socket timeouts are idle limits, not total deadlines. Replay and recovery hold ambiguous partial files indefinitely and require an unimplemented operator reconciliation path. The archive receipt is not accepted by Viewer, and a separate delivery and exact acceptance chain is still needed.

An explicitly injected, default-off Viewer service can serve the sealed coordinator spool through the existing authenticated NodeODM-compatible archive URL. It rechecks the exact task incarnation, claim, metadata and receipt, retains the spool lock during streaming and verifies the hash before releasing the last chunk. Disconnects, successful reads and receipt creation do not mark Viewer acceptance or delete either copy. Previously transmitted bytes cannot be retracted if authorization or identity changes during a stream. This experimental path is not wired to runtime startup.

Viewer maps provider status code 40 to upstream completion and enqueues ingest. The experimental worker's seal and metadata do not durably prove that the engine actually completed: a generic capture can create the same seal, and the coordinator has only a self-reported status. Therefore this adapter deliberately leaves the job running or held; a normal Viewer that waits for status 40 will not automatically ingest. A separately authenticated and durable completion proof, plus exact downstream acceptance and recovery, remain necessary before emitting success or enabling cleanup.

The synthetic tests use an actual TLS coordinator endpoint, temporary files, process interruption and an isolated container. The 10,000-entry test exercises coordinator metadata only; it does not establish transfer throughput, real reboot behavior, 50 GB capacity, Viewer integration, or an end-to-end production workflow. No live NodeODM or TrueNAS is involved.
