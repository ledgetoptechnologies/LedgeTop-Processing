# Large synthetic v2 transfer observation

An isolated run at Processing commit `01e336d70714f09d1123a40f6de98b0b3b7877f0` streamed a 1,074,790,538-byte synthetic ZIP through the fixture-only v2 TLS path in 1,026 chunks, promoted the spool, and downloaded it through the Viewer-compatible HTTP endpoint. The reported SHA-256 was `a1edd9b398d2f4f0b224bb66fa77ca51bbd896f58f534c655397516d7bb522c5`. Node and coordinator output files each reported 1,074,798,592 allocated bytes via `st_blocks`; this is filesystem allocation evidence, not a guarantee of physical hardware durability or capacity under thin provisioning.

The isolated container was limited to 0.5 CPU and 512 MiB, reported peak Python RSS of 47,840 KiB and elapsed time of 485.19 seconds, and did not acknowledge Viewer custody. It used a simulated engine and synthetic data, not real photos or a production job. It did not test interruption or restart of the large transfer, a 50-GB workload, Viewer acceptance or production deployment. The owned test container and synthetic data were removed; the task-owned evidence log was retained on the processing host.

The original executable probe has been removed because its internal guard did not independently prove container, image, source and mount ownership and could expose unrelated temporary data to cleanup. Future reuse requires a reviewed owner-verifying disposable-container wrapper with exact immutable image and source identities, unique labels, verified mount identity, a nonempty unpredictable marker, bounded execution and cleanup by verified immutable container ID. A prior successful run is not a substitute for those controls.
