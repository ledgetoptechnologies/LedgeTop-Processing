# Proposed authenticated paged-source snapshot provisioning (not implemented)

There is no deployed owner-authenticated Viewer signature or durable trusted-loader contract for paged source-frame pins in the prepared v3 store. The store does persist owner principal/environment, coordinator authority, task/attempt, envelope and normalized v1 submission, but those do not authenticate the proposed paged inventory, selected ordinals or their source custody. Its current v1 manifest ceiling also prevents the intended large input. An HTTP ingest route must remain unavailable. This is a proposal for Viewer/Processing review, not an agreed wire contract, route, authorization, or production implementation. An isolated synthetic read-only verifier exists, but neither it nor its test providers are mounted.

## Proposed signed statement

A bounded UTF-8 closed JSON statement would contain exactly `protocol`, `schemaVersion`, `issuerId`, `keyId`, `snapshotId`, `principalId`, `environment`, `coordinatorAuthorityId`, `jobId`, `generation`, `submissionId`, `activationId`, `viewerTaskId`, `viewerAttemptId`, `preparedEnvelopeSha256`, `datasetId`, `datasetManifestSha256`, `pipelineDigest`, `sourcePageHashes`, `sourcePageBytes`, `sourceCount`, `selectedPageHashes`, `selectedPageBytes`, `selectedCount`, `inputManifestSha256`, `processingClosureSha256`, `gcpEvidenceSha256`, `sourceRevision`, `revocationEpoch`, `issuedAt`, `expiresAt`, and `signature`. `gcpEvidenceSha256` is null only when no generated GCP is selected. Page hash and byte arrays are ordered, equal-length per stream, at most 64 entries each, with each page bounded by the negotiated frame maximum and aggregates/counts bounded by agreed policies. IDs, hashes, integer/non-bool fields, timestamps, duplicate keys, array lengths and total raw bytes need explicit fixed limits before decoding. Empty inventories, ambiguous source identities and unsupported versions hold.

For discussion, signature could be Ed25519 over `LTDS-VIEWER-PAGED-SOURCE-SNAPSHOT-V1` plus NUL followed by RFC 8785 canonical JSON of the statement excluding `signature`; signature encoding could follow the existing accepted-copy receipt's canonical unpadded base64url. These are proposals, not proof that Viewer signs or accepts this representation. The Viewer signature contract, exact domains, canonicalization, key provisioning, secure time semantics, page byte accounting, GCP evidence schema and compatibility must be agreed and cross-language tested before code accepts them. A signature authenticates the issuing key and fields, but does not itself prove source bytes, immutable custody, GCP correctness or future revocation status.

## Independent provisioning and trust

Processing operators provision a separately managed, bounded registry mapping `(principalId, environment, issuerId, keyId)` to an Ed25519 public key, purpose `paged-source-snapshot`, allowed coordinator authority and key lifecycle/revocation information. No public key, allowed scope, authority, trusted epoch, policy or snapshot is accepted from the HTTP request. Reject ambiguous duplicate key IDs, keys shared across unintended principals/environments/purposes, unknown/revoked keys, untrusted issuers, and unsupported versions. Existing accepted-copy receipt keys do not automatically authorize source snapshots; deliberate separately reviewed provisioning is required. Secret signing keys stay with Viewer.

Viewer must construct source rows, stable dataset-file IDs, selected ordering and generated-GCP evidence from one coherent immutable dataset/attempt transaction. Its signed statement must bind the exact source/selection frame bytes, the original nested paths/roles/dispositions and stable IDs, selected engine ordering, generated attempt GCP size/hash and source-correspondence evidence, and retained raw GCP custody. It must not derive dataset IDs by inventing values from provenance paths. It must sign the exact prepared attempt/envelope and coordinator authority after independent identity checks. Actual role/selection semantics, nested paths, `inputManifestSha256`, GCP substitution and LiDAR MIME/kind need direct Viewer 551+ implementation and fixtures. Current source/frame proposal remains a draft.

## Transaction and replay contract

With protected transport, one unambiguous bearer identity and exactly one independently configured expected-authority header, Processing begins a transaction and rechecks current authority/lease, authenticated principal/environment, owner-scoped prepared submission, persisted task/attempt/activation ID, envelope and pipeline/manifest binding. It loads the registry and current epoch from trusted server-side configuration/state, verifies signature and version, then compares every statement identity to that same transaction's stored values. Wrong owner is indistinguishable from missing; wrong authority or unavailable trust holds. Request-provided fields only become usable after these checks.

A durable uniqueness key should bind `(authority, principal, environment, submissionId, viewerAttemptId, snapshotId, epoch)` to the statement hash and exact source/selected/closure pins. Exact replay returns the already staged held outcome after rechecking persisted page integrity and current authority/epoch. A changed statement, changed key identity or attempt, or reused snapshot ID with different bytes is a conflict; a revoked or stale epoch holds. New attempts never silently reuse old reservations or retry budgets. Binding, statement and pages must become visible atomically, including crash after commit/before response. Incomplete or disconnected input must not make any partial state authoritative. Durable disk quota and reservation must be checked before ingest; source/selected pages must be bounded and parsed incrementally; expected counts/hashes and authenticated selected ordinal mapping must exactly match a separately pinned processing closure.

The `1453e20` receiver currently owns a separate dedicated SQLite transaction and rejects an already-active transaction. It cannot simply be called from the prepared-store transaction: doing so would either split authority from staging or collide with transaction ownership. Integration requires a reviewed same-database transaction API that writes to an owned cursor without nested commit/rollback, a coordinated schema and migration, writer fencing, and cross-process concurrency tests. No partially verified pages may be promoted merely because one transaction committed. Replay after restart must revalidate stored bytes and the independently loaded current authority/epoch, not trust a prior unexpired signature alone.

Viewer and Processing need a continuously enforceable revocation/fencing model for each transfer: validate before streaming, at bounded intervals or chunks, after streaming, and in the commit transaction. Authentication failure, ambiguous state, concurrent revocation or lost connectivity holds and preserves existing data. A signed static epoch is insufficient unless compared with independent current authoritative epoch/lease state and an agreed fencing mechanism.

## Required synthetic validation before wiring

Test the real Viewer producer and Processing reader with 16,832 synthetic files, retained GCP and generated attempt GCP, nested Unicode paths, LiDAR MIME/classification, exact Viewer `JSON.stringify` input digest, page boundaries and canonical byte vectors. Exercise wrong or duplicated authority headers; wrong bearer/owner/environment/task/attempt/dataset/envelope; unknown/rotated/revoked/wrong-purpose keys; forged signature, stale/current epoch and concurrent revocation; altered, missing, duplicated, reordered, oversized, truncated and extra pages; conflicting and idempotent replay; simultaneous writers; exhausted disk/quota; process death before/after commit; restart and data corruption. Verify zero partial committed rows for failed ingest, and all cleanup/source-grant/activation routes stay held. Real filesystem/power-loss and scale qualification remain separate.

## Inactive synthetic verifier

`paged_snapshot_signature_candidate.py` tests this proposed exact signed field list against a separately supplied purpose-scoped Ed25519 key registry and the actual owner-scoped prepared store. It revalidates the stored prepared envelope/policy, authority, owner/environment, task/attempt, generation, dataset manifest and pipeline. Its test-only epoch and exact snapshot-pin providers are independent caller-supplied functions and MUST be replaced by authenticated durable server-side authorities. Without either it returns `held/trusted_snapshot_or_epoch_unavailable`; with both matching it still returns `held/atomic_staging_unavailable`. It makes no staging writes and has no replay ledger; repeating a statement merely repeats read-only inspection, not a durable idempotency or conflict guarantee.

For this draft, each page-byte count is canonical JSON bytes excluding the mandatory LF delimiter; per-frame hashes likewise exclude LF, while the total stream byte budget includes one LF per page. Hashes and byte arrays are ordered and equal length. Each frame has 1–512 records, so declared counts must be between the page count and 512 times the page count; actual record counts, sizes and `gcpEvidenceSha256` null iff generated GCP absent cannot be established until all authenticated frame and GCP evidence bytes are checked transactionally. `sourceRevision` is presently only a bounded opaque signed token: it is not provisioned from an authoritative immutable revision and must not be trusted as one. Viewer must decide whether to omit it or define and supply a transactionally bound immutable identifier. The candidate cannot prove its immutability, uniqueness or meaning. `processingClosureSha256` must eventually be computed independently from the exact validated selected record order and pinned in the prepared closure; Viewer does not currently compute it. A signed caller-provided value is not that independent validation. These fields are included for contract discussion and do not waive those holds.

`issuedAt` and `expiresAt` use exact UTC millisecond syntax, and the synthetic verifier rejects nonpositive or greater-than-one-hour claimed TTL. It does NOT compare with a trusted current clock or authorize an unexpired token. A production mechanism must use independently trusted time and define skew, expiration and replay retention. The verifier uses the reference canonical JSON routine only on a strictly closed statement of ASCII keys/identifiers, hashes, timestamps and nonnegative safe integers; cross-language RFC 8785 vectors are still required for the eventual producer.

One key is not accepted across different principal/environment scopes by the prototype registry. Key revocation, issuer namespace governance, actual key lifecycle, replay ledger, same-database atomic receiver integration and active stream fencing are not implemented. Tests use ephemeral synthetic keys, real prepared-store records, wrong keys/scopes/attempts/pins/epochs and repeat/reopen reads; they establish no Viewer signer, actual broker, protected HTTP or end-to-end processing.

Issuer/snapshot reuse must be governed by a durable cross-job/cross-attempt uniqueness registry. The current read-only candidate has no such registry and must not be treated as enforcing replay or conflict protection. `gcpEvidenceSha256` must identify the separately agreed complete immutable evidence, not merely a correspondence-row digest; no such complete-evidence producer is currently verified. The future receiver must reconstruct the processing closure independently from the authenticated selected records, with exact negotiated 512-object page partition and page/closure domains; checking a submitted closure hash alone is insufficient. All remain activation blockers.
