# Provisional v2 metadata ledger

This explicitly opt-in internal prototype stores v2 submissions, worker metadata claims, plans and reservation envelopes in a separate SQLite table owned by the coordinator queue. It does not enter the execution scheduler or authorize processing, so a staged v2 record cannot block or overlap a v1 production job. The caller must obtain principal, environment and capability fingerprint from a separately authenticated future transport. No endpoint is installed and no credentials authenticate the producer here.

Records support identity-bound replay and remain persisted after restart, but metadata claims are tied to the coordinator startup ID and become held after restart; there is no automatic reacquisition. The current-epoch snapshot returns canonical manifest, plan and envelope bytes after verifying their stored digests and bindings. It does not authenticate the broker, prove file custody, confirm charges or authorize a transfer. Revalidation at point of use is still necessary: a pre-return expiry check does not guarantee availability or validity after return.

The 64 MiB default is a cap on the aggregate JSON text in this table, not total database, WAL, filesystem or disk usage. Validation and hashing occur while the local admission gate or SQLite transaction may be held, so admission close and other operations can be delayed. The table schema is checked on open; restore, power loss, older-binary access, retention, cleanup, recovery and deployment are unqualified. Large synthetic object-count tests establish metadata handling only, not sustained throughput or delivery.
