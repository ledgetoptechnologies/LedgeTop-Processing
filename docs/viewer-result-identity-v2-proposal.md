# Proposed Viewer result identity v2 - review draft

This is a proposed contract, not an implemented endpoint, authorization policy, rollout, receipt of Viewer custody, or permission to delete data. Existing closed v1 request and response types remain byte-for-byte unchanged. Both owners must approve exact fields, canonicalization, indexes and failure semantics before implementation. Legacy jobs lacking authoritative canonical input/pipeline identity remain on their existing path and are **ineligible** for this commitment; do not fabricate fields.

## Authority and scope

Processing authenticates a distinct provisioned Viewer service principal over server-authenticated TLS. An explicit authorization policy binds that principal to environment, coordinator authority/audience and eligible job/generation. The bearer is sent only in the Authorization header, is never written in a commitment, URL or logs, and is checked afresh for every request including replay. A shared production/staging token that identifies only an environment is insufficient. Provisioning, rotation and how physical fences are established are prerequisites, not features implemented here.

Processing job ID/generation and coordinator authority are Processing identities. Viewer task ID and attempt ID are authenticated **claims made by Viewer**; Processing cannot infer their membership from the service credential. Viewer validates their durable mapping to the Processing job and generation against its own authoritative database before registration and after every response. Neither a commitment nor an authenticated claim proves Viewer acceptance or storage. For this proposed schema, `principal` is the authenticated binding-claim issuer, and `authorityId` identifies the Processing authority issuing the commitment; they are distinct identities. The client must validate TLS and map the authenticated endpoint to the expected authority/audience via trusted configuration, then verify all response fields; a certificate or DNS name alone does not establish that mapping. This proposal does not claim a portable signed proof.

The proposed separate, opt-in routes are `GET /ltds/v2/capabilities`, `PUT /ltds/v2/viewer-bindings/{bindingId}`, `GET /ltds/v2/viewer-bindings/{bindingId}`, and `GET /ltds/v2/viewer-bindings/{bindingId}/commitment`. Capabilities explicitly names this v2 and its serializer. A missing capability/route means use existing v1 behavior only, with **no** claim of this stronger binding. Routes, media type and client fallback require Viewer sign-off. The path UUID and body `bindingId` must match. No v1 fields are added or reinterpreted.

## Canonical bytes and hashes (proposed)

Binding object is closed to exactly `schemaVersion`, `bindingId`, `principal`, `audience`, `profile`, `authorityId`, `environment`, `processingJobId`, `processingGeneration`, `viewerTaskId`, `viewerAttemptId`, `expectedReceiptSha256`. `schemaVersion` is integer 2; environment is exactly `production` or `staging`; UUIDs use lowercase canonical hyphenated spelling; generation is an integer 1..9007199254740991. `principal`, `audience` and `profile` are case-sensitive ASCII slugs `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`. Viewer additionally validates any mapping across environments or coordinator authorities in its own database; Processing cannot infer cross-scope uniqueness. Processing job IDs in this proposed v2 are UUIDs; non-UUID legacy IDs are ineligible until a separately reviewed type is agreed. Principal comes from server-side credential provisioning, while audience and authority come from authenticated server configuration and policy. They must exactly match the body and the expected TLS endpoint, not be trusted from the body or DNS name alone. `profile` is selected from a negotiated immutable registry and binds the exact receipt format/version, input inventory and pipeline canonicalization and digest provenance. `viewer-result-v2.1` in the vectors is an illustrative unregistered profile, not an eligible production mapping. A changed mapping requires a new profile identifier; missing or unknown profile is ineligible. `expectedReceiptSha256` is null unless Viewer admission has already durably fixed the exact intended receipt digest; if non-null it is immutable and the commitment must match it. Do not populate it from a later Processing result and present it as prior Viewer intent.

Commitment object is closed to exactly `schemaVersion`, `bindingSha256`, `profile`, `archiveSha256`, `archiveBytes`, `receiptSha256`, `inputManifestSha256`, `pipelineSha256`, `resultManifestSha256`. SHA-256 fields are 64 lowercase hex characters; `archiveBytes` is an integer 22..9007199254740991. `resultManifestSha256` is null only when no canonical producer result manifest exists; it must never be an invented manifest. `profile` must exactly match the binding and the immutable negotiated registry. `receiptSha256` is SHA-256 of the **exact retained receipt file bytes**, not of reparsed or reformatted JSON. Its format/version, input-manifest canonicalization and pipeline canonicalization must each be identified by the negotiated v2 profile before a real commitment is eligible. The JSON object does not carry secret material.

For these flat schemas only, canonical bytes are UTF-8 JSON with lexicographically sorted ASCII keys, no insignificant whitespace, integer decimal without exponent or leading zeros, JSON null, and ASCII string values with JSON escaping as required. Validate the raw UTF-8 stream before ordinary JSON decoding: reject invalid UTF-8, duplicate keys (including duplicates spelled with JSON escapes), unknown/missing fields, non-ASCII/control characters after unescaping, booleans in integer fields, and any numeric lexeme except canonical unsigned decimal integers (`0` or `[1-9][0-9]*`); reject `-0`, `1.0`, `1e0`, and out-of-range values before JavaScript number coercion. Decode equivalent JSON string escapes before validation and canonical re-encoding; reject alternate UUID/hash spellings. Apply fixed request and field-size limits before parsing; exact numeric caps require cross-language review. Implementations must compare their output byte-for-byte on the vectors below; never hash arbitrary incoming JSON bytes. Binding digest is `SHA256(ASCII("ledgetop.viewer.binding.v2") || 0x00 || canonicalBinding)`; commitment digest uses `ASCII("ledgetop.viewer.commitment.v2") || 0x00 || canonicalCommitment`. `0x00` is one binary NUL byte.

Negative vectors: adding a duplicate `bindingId` or escaped-equivalent `"\u0062indingId"`, including malformed UTF-8 or a non-ASCII escaped value, changing generation to `1.0`, `1e0`, `-0` or `true`, uppercase hex/UUID, adding `token`, or replacing `null` with an invented manifest digest must fail validation or eligibility. Whitespace/key order differences in otherwise valid request JSON canonicalize to the same binding; a field change does not. Receipt hashing is over the exact file bytes and therefore does not normalize whitespace.

## Durable transition and exclusion requirements

A first authenticated PUT creates a **provisional** immutable binding transactionally. Global uniqueness is scoped by `(authorityId, environment, bindingId)`, with immutable principal and audience; reverse conflict keys cover `(authorityId, environment, viewerAttemptId)` (the Viewer task ID is immutable within that binding) and `(authorityId, environment, processingJobId, processingGeneration)`. Exact treatment of intentional multiple consumers requires a future explicitly versioned policy, not a silent exception. Durable tombstones retain these keys after any revocation or lifecycle change; they prevent reuse and cross-principal rebinding. A same-principal identical retry after fresh authentication returns the same binding; changed bytes, changed principal, conflicting reverse keys or stale generation never create a second binding. Responses must not directly disclose another principal or its binding contents. A create-versus-collision response (201 versus 404/409), timing, or reverse-key probing can still reveal occupancy; uniform error bodies alone do not solve this oracle. Do not claim cross-principal non-disclosure until mitigation is agreed and tested. Possible options requiring review include principal-scoped server-issued unpredictable binding IDs, response normalization and rate limits; reverse-key collision behavior remains unresolved.

A commitment may be recorded only after a stable retained archive and exact receipt bytes are read and hashed while the actual physical single-writer fence and the relevant file/receipt exclusion remain continuously held, binding retained open descriptor, mount/inode identity and exact bytes through durable commit. The same barrier must cover durable commit and task/generation/hold/authority validation; a fresh database recheck after dropping the physical fence is insufficient. Any lock loss, uncertain writer, missing receipt, changed inode/content, invalid source or unqualified storage holds without commitment. The archive hash is computed from retained bytes, the receipt hash from exact retained receipt bytes, input and pipeline hashes must come from their named immutable authoritative formats, and any result-manifest hash must come from an actual producer manifest with separately qualified provenance. Matching digest shape alone proves none of these origins. The archive hash is not source authentication or Viewer custody. Fencing old binaries, mount aliases, host/Docker administrators and recovery from fence loss are not solved by this document.

Provisional and committed records persist across restart. Once committed, exact replay returns identical canonical fields and digest; any different archive, receipt, input, pipeline, authority or generation is a conflict requiring inspection. Revocation/expiry policies restrict **new authorized requests**; they do not rewrite an existing proof or retract transmitted bytes. No expiry duration, clock-skew tolerance, freshness window or automatic revocation policy is selected here. Freshness/authentication must be specified separately before use.

## Failure and response proposal

| Condition | Proposed external result | Required durable effect |
| --- | --- | --- |
| Missing/invalid/revoked credential | 401, fixed sanitized error | No write or secret echo. |
| Authenticated but unavailable/not authorized identifier, including another principal's | 404, same fixed error | No explicit owner details; occupancy/timing oracle remains unresolved. |
| Valid principal, malformed closed schema | 400, fixed sanitized error | No write. |
| Same authorized principal, exact PUT replay | 200, identical provisional/committed record | No second binding. |
| Fresh valid binding | 201, provisional record | Commit once under unique keys. |
| Authorized changed payload, reverse-key conflict, stale generation or changed authority | 409, generic conflict | Preserve prior binding/tombstone; no new result. The chosen collision status may mask details but does not eliminate occupancy or timing leakage; policy and mitigation remain unresolved. |
| Provisional job has no qualified retained result, missing canonical input/pipeline or unknown manifest provenance | 409, fixed `identity_not_ready` or `identity_ineligible` | No commitment; legacy processing remains available. |
| Hold, physical fence loss, unavailable storage, ambiguous prior write or failed revalidation | 503 or 409 per reviewed transient/inspection taxonomy | Preserve all artifacts and intent; never issue or revise a commitment. |
| Commit response lost after durable write | Client performs freshly authenticated GET; exact immutable record returns | No duplicate, no silent replacement. |

The route must use bounded request/response bodies and sanitized errors. Capabilities, binding and commitment responses must authenticate, use TLS, set `Cache-Control: no-store`, carry a negotiated versioned content type, and reject redirects and oversized bodies. Exact content type remains subject to joint approval. Client timeouts and lost PUT responses are ambiguous: use a fresh authenticated lookup or exact retry, never assume failure. Cancellation/revocation semantics for an in-flight PUT require joint agreement and must not silently commit after a hold; data and intent remain held on ambiguity. A status code is not evidence that an in-flight stream was revoked. An archive download must separately bind and verify the exact bytes and generation consumed; a commitment lookup followed by an unfenced unbound download is insufficient. No acceptance endpoint, Viewer ingestion, queue completion, deletion or cleanup is authorized here.

## Required review and tests

Before enabling: cross-language canonical vectors and negative encodings; real distinct-principal/environment/audience authorization; Viewer-owned database membership validation; both directions of uniqueness and durable tombstones; identical replay/lost response/crash at each commit boundary; stale generation, changed authority and revocation; concurrent binding/hold/cancel races; independent source/receipt/file hash verification under a continuously held fence; no publication if physical exclusion is unavailable; secret-free logs; and migration/backup/rollback of nonempty state. Tests must distinguish no result manifest from an actual canonical one and demonstrate legacy v1 remains unchanged. Current PR187 is not eligible and no data or route is modified by this proposal.
