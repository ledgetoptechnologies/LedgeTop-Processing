# Concrete transport foundation — not an activation controller

This checkpoint supplies structured, bounded Docker CLI execution, closed
container recipes, private configuration readback, operator HTTP and exact
read-only Gate receipt scripts, physical binding observation, and an original
main/external-flock holder. It does not yet implement the journal's phase driver,
backup/projection orchestration, or a qualified deployment recipe. It performs
no action on import and has not activated or changed an installed coordinator.

The initial ten focused tests passed on Linux in 0.630 seconds under UID 10001,
network isolation, one CPU, 768 MiB, a read-only worktree and bounded tmpfs. The
holder tests acquired the actual original main and external flocks, denied
competing holders, rejected forged descriptor proof, then released and verified
unchanged original files. The exact task container was removed. Three subsequent
tests add synthetic Docker-copy tar validation, read-only receipt-script checks,
and owned descendant timeout cleanup; the seven portable cases passed locally.
The expanded Linux suite has not yet been rerun at this checkpoint. No actual
Docker create/cp deployment qualification is claimed by these tests.

The expanded suite subsequently passed 16/16 Linux cases in 1.150 seconds,
without skips, under the same bounded isolation. It additionally checks the
fixed existing installation lock and persistent exact-operation binding, private
immutable evidence, distinct rejection artifact names for each dispatch attempt,
directory-replacement refusal, and owned descendant timeout cleanup. The exact
container and task-label inventory are absent after completion. The active-plan
binding is intentionally retained on disk after lock release: another receipt
directory or operation does not authorize a competing cutover.

Independent review identified a post-acquisition sentinel failure gap. The
helper now catches proof-publication and ongoing identity/check failures after
external-lease acquisition, retains every acquired descriptor and waits for an
explicit release signal. A best-effort held marker invalidates prior readiness;
failure to publish that marker never causes process exit. Both ongoing-check
and proof-fsync faults are qualified with actual children and competing original
kernel flocks. The affected suite passed 18/18 Linux cases in 1.869 seconds with
verified task-container removal. Mounts below `/etc` are also refused.

Local Docker CLI timeout cleanup does not prove the remote Docker-exec Python
process exited. Its lifecycle and safe retirement before holder release remain
an explicit incomplete transport predicate at this checkpoint.

## Historical pilot record provenance

A bounded local history lookup located the original operator artifacts:

* `two-node-acquire-supervisor-DRAFT.py`, SHA-256
  `65c80f8e7d69dee6491ad6c318519cc0f345fdc0a439649399fe5a30b84b59e0`.
* `owned-node-drain-DRAFT.py`, SHA-256
  `b68a64c4a14004b302a5386ab6fb95d96b5a19ef7ad073af55e05948a6a4f277`.

The acquisition supervisor's wrapper writes each node's start and exit marker
from the same Docker-exec child in the coordinator container. The node denotes
the target maintenance schedule; even the main-node acquisition child executes
in the coordinator PID namespace. Each marker is an exclusive, private,
fsynced `{pid, boot, start}` record; the exit marker is written in `finally`.
It proves neither successful scheduling nor successful cancellation.

A read-only probe of the retained records checked all six sibling groups
against those exact closed schemas. All marker pairs, operation-directory,
node and authority correlations matched. The recorded boot matches the current
container boot, and none of the recorded PID/start identities is live in that
container namespace. The two additional cancellation-intent fields are
`proofSha256` and `archiveSha256`.

This establishes the recorded acquisition-child identities and their absence.
It is not a complete pilot-closure certificate: the local supervisor and later
release-process lifecycle, exact owned scheduling/cancellation receipts and
retained output custody remain separate predicates. The retained artifact
sources currently contain explicit disabled draft guards; this checkpoint does
not claim their bytes alone establish which approved execution occurred.
Host-PID absence must never substitute for the container-namespace check.

## Remaining concrete path

The phase driver must consume the single reviewed journal and independently
generated policy, bind every mutating completion to its current dispatch nonce,
retain uncertainty without replay, and obtain actual stopped-writer/physical
lease custody before backup or projection verification. It must qualify the
same-image bootstrap/final recipes and authenticated final runtime/worker
readiness before reopening. Missing pilot, NAS, legacy-delivery or worker gates
remain holds; this checkpoint does not create those authorities.

## Lifecycle follow-up

The holder now supplies positive in-memory ready/held responses on its private
Unix socket. The observer verifies the actual peer PID/UID, fresh challenge,
settings and start time before checking original FD/kernel-flock identities.
Even simultaneous proof-fsync and failure-file publication errors cannot turn a
visible old proof into readiness. Exact local proof replay repeats verified
file and original-directory fsync barriers before yielding the fixed host lock.

`TrackedExec` reserves each exact container/request/source digest durably before
dispatch. A lost local reply is inspection-only; any existing reservation,
including partial/malformed evidence, prevents redispatch. Its remote helper
retains private bounded start/result/exit records. Retirement requires matching
records and absence of the actual PID/start identity; an exit marker while that
PID remains live is insufficient. These records establish helper lifecycle,
not whether an operator mutation occurred. The journal still verifies effects.

The expanded foundation suite passed 25/25 Linux cases in 3.370 seconds without
skips, under one CPU/768 MiB/network-none/UID10001/read-only worktree. Actual
process tests include live-PID refusal, missing-exit refusal, lost-reply recovery
without redispatch, sentinel failures, original competing flocks and owned local
descendant cleanup. Streaming TAR output is bounded without whole-archive
buffering and returns a receipt only after clean EOF and client exit zero.
That receipt alone does not validate archive custody or remote daemon effects.
The exact task container and task-label inventory were absent afterward.

The production holder additionally requires non-init PID1, checks fixed reviewed
read-only `/app` package origins under isolated Python, and waits for all other
live namespace processes to exit before releasing original locks. These exact
Docker/PID1/package predicates still await the independent task-owned Docker
harness; the ordinary subprocess suite does not qualify them. No installed
coordinator, NAS files, live jobs or actual cutover were changed.
