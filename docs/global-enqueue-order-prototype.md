# Disabled global enqueue order prototype

An explicitly constructed migration adds an append-only AUTOINCREMENT ordering record in the coordinator SQLite database and insert triggers for the existing legacy, Viewer, v1 ReferenceStore and v2 metadata enqueue paths. Existing v1 jobs are seeded in their original sequence in one transaction. Migration refuses pre-existing v2 metadata because its historical order relative to v1 cannot be reconstructed. V2 staging schema and order triggers are installed together. This is not automatically enabled or consumed by the scheduler.

V2 promotion into the jobs table uses the original v2 ordering identity only when a matching staged record exists; that identity alone does not authorize a worker, validate a broker grant or establish readiness. `pending_page` reports current queued v1 jobs and unpromoted or promoted-but-queued v2 metadata in production-before-staging, enqueue order within each class, using a keyset query with a bounded result size. V2 metadata is not necessarily eligible. Each page is a separate snapshot; a consumer can miss newly arrived production or earlier entries whose eligibility changes between pages. Pages are diagnostic only and cannot be used for dispatch without a fresh transactional head and eligibility check. Existing scheduling code does not yet call this method.

History is retained as tombstones and the diagnostic full snapshot refuses more than 1,000 rows. Pagination does not materialize full history, but an indexed scan may still traverse many tombstones; trigger/schema verification can scan current rows. Retention, storage quotas, compaction, high-volume performance, authenticated writes, backup/restore, older-binary compatibility and live migration remain unqualified. Trigger checks are not protection against an actor with arbitrary database or schema write access. No execution is enabled by this prototype.
