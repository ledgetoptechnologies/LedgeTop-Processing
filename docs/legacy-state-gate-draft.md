# Disabled legacy coordinator lifetime fence prototype

This prototype is not wired into the image command, deployment configuration, or updater. It must not be deployed as a complete cutover solution.

The optional `python -m processing.legacy_state_gate` entrypoint opens and exclusively locks `/legacy-state/coordinator.lock`, validates that the candidate state is a different lock inode, and executes the candidate coordinator in the same process while retaining the open lock descriptor. The legacy coordinator itself takes an exclusive lock on `coordinator.lock` before writing its state. If both use the exact same stable legacy lock inode, at most one can hold that lock: candidate-first makes the old process refuse; old-first makes the candidate refuse before it starts. A process crash releases the lock. A new candidate racing an old process after restart must acquire it again. The process holding this gate is the candidate itself, avoiding a separate holder's crash interval while the candidate continues running.

This is conditional, not a complete cross-host or reboot fence. The trusted cutover supervisor must bind the exact original legacy volume read-only at `/legacy-state`, enforce this entrypoint on every candidate start, exclude restores and inode replacement, and ensure every Docker/systemd updater and old coordinator uses that same retained legacy state. It must prevent a coordinator starting from any other retained copy with the same authority. There is no persistent marker or mandatory startup integration here. A privileged or misconfigured actor can bypass the wrapper or mount a different volume, and neither systemd unit ordering nor a host/daemon reboot was tested. Closing or changing the inherited descriptor or untrusted changes to the filesystem can invalidate assumptions. Additional validation, an explicit rollout/rollback plan, and old-updater controls are prerequisites.

Local evidence: four Linux process tests cover exclusion, inherited descriptor across exec, process kill, missing/symlink refusal, and candidate lock identity. A network-disabled Docker Desktop experiment used d738-source-matched synthetic old image `sha256:6c5d7eb6c9cfd57f2c1fc3a5d986ccf4e19aace8e14914d2810ca30801f76af7` and prototype candidate image `sha256:aeda447b7df8e57ec32bbd225490c5c6c829ad159efc03c51aa5dd72cb3dd051`: both startup orders and Docker `restart=always` old retries were refused on the actual same retained lock. The owned synthetic container and volume label censuses were empty afterward. No real daemon restart, OS reboot, systemd updater, production state, or client data was tested.
