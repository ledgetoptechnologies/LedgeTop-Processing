# Large source capacity audit (synthetic, inactive)

The reference protocol currently cannot admit a 16,832-image survey. The real dataset was not read or submitted and no image bytes were created. Do not split a survey automatically. This is an audit and a version-design outline, not a new admissible protocol.

A synthetic manifest with 16,832 distinct image records and 152,992,006,528 declared bytes serialized its object array to 2,979,265 bytes; actual names and submission fields can increase the total. The complete synthetic submission serialized to 2,979,925 bytes; constructing and serializing it took 0.30 seconds and 12,441,074 bytes of peak Python-traced allocations in one local run. This does not measure process RSS, parsing, concurrency, actual paths, or processing. It is below the current 4 MiB limit in this fixture, while current v1 rejects more than 10,000 objects. The prepared JCS parser separately rejects more than 100,000 JSON value nodes. Source and result accounting also use 10,000-item ceilings in multiple contracts and implementations. Raising just one constant would not produce a usable compatible system.

The candidate source-range request builder uses 8 MiB chunks. This synthetic distribution makes 33,664 unique range intents and permits 100,992 HTTP attempts and 458,976,019,584 budgeted bytes under its 3x attempt and byte budget. The byte budget counts unique range intents rather than retransmitted network bytes; retries are controlled separately by the attempt budget, and actual network use can exceed the byte budget. Repeating the builder returns identical metadata, not a test of real retry, reconnection, authorization, or ledger durability at scale. A checked-in separate broker policy example has a 64 GiB manifest cap and a 16 MiB chunk size; these example values are not proof of current configured broker policy, and disagreement must be reconciled before deployment.

ReferenceStore defaults to 64 MiB total metadata quota and records multiple serialized copies of prepared metadata; quota and actual SQLite/WAL growth must be measured rather than assumed. Source-range ledger records objects, range intents and budgets in SQLite; its per-object lineage census performs SELECT DISTINCT over prior source objects, requiring a scaling review. The source-range candidate does not establish free-space admission by itself. Node staging, output products, engine scratch, transfers, retries, and retained copies require measured headroom; 153 GB source size is not the job's disk requirement. The local node's default policy is 1,000 photos and 20 GiB; routing and live node limits must be verified independently.

A future versioned large-source protocol needs explicit negotiated count, per-file/aggregate/whole-message limits and immutable manifests, bounded parsing and durable transactional accounting, exact cross-service policy/attempt identity, source-range retry and revocation tests, and no existing v1 compatibility changes. Pagination/chunked manifests may reduce per-message resource exposure but need ordered closure, digest and replay semantics agreed with Viewer and broker. Benchmark metadata memory, SQLite/WAL and runtime under a representative 16,832-object manifest; then test retry, worker restart and final Viewer acknowledgement with small synthetic payloads. Measure disk, CPU/RAM and actual NodeODM limits separately before a real large job. GPU capacity or completion times are unknown.

Tests: `python3 -m unittest tests.test_large_source_capacity_audit -v`.

A separate broker audit found a whole-file digest is recomputed for each 8 MiB range, a global 100,000-row census bound, a five-minute default/one-hour maximum lease, and per-chunk fsync. On large jobs these are material scaling concerns; the actual route and deployed configuration still need confirmation.

One candidate successor would negotiate a separate version and a bounded, paginated ordered manifest and integrity tree, committing the survey's full object closure and digests. The trusted source service would bind the grant and ledger to an immutable snapshot or equivalently protected source identity, size and digest; compute file and chunk commitments once against that immutable identity, and use authenticated chunk proofs/digests on every range. A mutable source or changed stat/identity must hold the transfer and require a fresh authorized snapshot, not silently trust cached hashes. Reservation attempts and range intents would stay transactional and idempotent across expiry and restart; bounded lease renewal would recheck source authority, revocation epoch and current authenticated principal before streams and during delivery. Ledger namespace indexes and bounded per-job accounting would replace full per-object scans. Any batched fsync design needs crash tests proving the ledger never claims durable bytes before the actual file and directory data are durable; until demonstrated, keep the conservative behavior. Design and implementation need Viewer, Processing and broker agreement; the outlined version has not been implemented or validated.
