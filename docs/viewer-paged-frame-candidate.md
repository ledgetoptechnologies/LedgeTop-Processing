# Viewer source frame experiment (inactive, held)

This is a bounded framing primitive, not an authenticated producer, Viewer integration, selection verifier, broker endpoint, dispatch authorization or accepted schema. The caller must supply an independently authenticated ordered page-hash list and item count. A successful return is always `held_no_viewer_authority_or_mapping`. It has no trusted snapshot loader and cannot prove the dataset is complete, that records came from Viewer, selection/photo-first order, MIME/kind, attempt/authority/epoch binding, real source bytes, retained custody or correspondence evidence. Existing runtime limits and v1 remain unchanged.

Draft format: each UTF-8 canonical JSON line (LF delimiter, excluded from hash) is `{version:"ltds-viewer-source-frames-v1",index,records}`. Page hashes are SHA-256 of ASCII `ltds-viewer-source-frame-v1`, NUL and exact canonical line bytes. The external pin must cover page order and expected total count. Bounds are 256 KiB raw per line, 512 records/page, 64 pages, 20,000 records and 12 MiB raw overall. Read and structural preflight precede JSON allocation. Strict type/duplicate-key checks and fixed closed shapes are enforced. Only standard `io.BufferedReader` or `io.BytesIO` streams are accepted; a BytesIO may already contain a fully allocated input, and reading from a network requires a separately bounded trusted adapter. Individual frame arrays and cross-page ID/path sets consume bounded memory; no process-RSS cap is enforced.

Two proposed record shapes:

- `{type:"dataset_file",datasetFileId,relativePath,byteSize,sha256,processingRole,mediaType}`.
- `{type:"attempt_generated_gcp",attemptId,byteSize,sha256,sourceFiles:[{datasetFileId,relativePath,sha256}],correspondenceSha256}`. At most one generated record is accepted; each cited source tuple must match a `gcp_source` record in these same frames. This is internal consistency, not independently validated correspondence or custody.

Do not freeze this schema until Viewer agrees. Its `getAttemptGcpEvidence()` at commit `5513f92b6cf45221475a3c38347e3ca1dbf0c32d` returns a full snapshot with correspondence rows and verifies generated content internally; a corresponding authenticated immutable same-transaction export, selected IDs and nested-path mapping, and stream revocation fence are missing. A separate run of the real Viewer repository test `each processing attempt snapshots deterministic private ODM correspondences` passed against its synthetic SQLite fixture. That test is not connected to this frame verifier. No captured production data was used.

On one synthetic run, 16,832 image records, one raw GCP record and one generated GCP record produced 33 frames / 4,311,812 bytes. Verification took 2.56 seconds with 4,194,437 bytes of peak Python-traced allocations after constructing the input in memory. This excludes input creation, process RSS, authentication, source-byte transfer and concurrent workloads. Tests reject truncated, reordered, oversized and extra frames, duplicate identities, Boolean byte size, duplicate keys and altered GCP source hashes, including when an attacker-controlled test pin is recomputed.

Viewer review: source frame order alone does not bind the actual engine inputs. A future authenticated binding must include Viewer's `inputManifestSha256` and the exact ordered selected mapping to stable file IDs and the generated-GCP selector, or an equally precise authenticated disposition/ordinal record. Source rows are in path order, while selected inputs are role filtered and photo-first. Production export must read dataset, current attempt and GCP evidence in one coherent SQLite transaction and independently authenticate/recheck revocation epoch before, during and after streaming. This primitive implements none of those protections. ASCII-equivalent Viewer extension classification and exact raw GCP displacement are also not implemented here.

A pinned Viewer `referenceProtocol.canonicalBytes` implementation is exercised by the paired-required Unicode-frame test. An adversarial nested-path test confirms that some 512-record pages exceed 256 KiB and must be split earlier; the object-count ceiling does not guarantee arbitrary maximum-length paths fit the page or aggregate limits. No paging producer is implemented.
