# Draft Viewer input inventory — disabled

This isolated prototype requires both an explicit TaskStore opt-in and a ViewerFacade opt-in; normal construction does not install its schema and the route returns 404. It is not wired into application configuration, not advertised, and not deployable. This isolated branch combines PR78 and PR79 using a shared exact schema bundle. A qualified cutover rehearsal, census allowances, and old-binary fencing remain prerequisites.

When explicitly enabled, `GET /task/{uuid}/ledgetop/input-inventory?token=…[&cursor=…]` is read-only and requires both the same environment token and reservation capability used by task routes. Legacy unreserved tasks are deliberately excluded pending agreement. Each request checks task environment, reservation and generation in one SQLite snapshot. The response includes task UUID, environment, generation, stage, epoch, revision, up to 100 files and an opaque nextCursor. Each file has the exact stored submitted name, current ASCII basename casefold nameKey, byte count, SHA-256, photo flag, and `recorded` or `pending_intent` state. No paths or capability values are returned.

Cursors are random tokens stored in a bounded 1,024-entry in-process map, not encoded filenames. They bind task, environment, generation, random process epoch, revision and last name. Eviction, restart or another TaskStore instance invalidates a cursor and callers must restart pagination. A transactional singleton revision is incremented by twelve SQLite triggers for task, reservation, file and intent mutations; all named schema is validated before reading. Each page reads revision and indexed records within one short SQLite snapshot. Unrelated task mutations also invalidate cursors. Installation is transactional; partial or changed named schema fails closed. The revision design assumes trusted database ownership: unauthorized schema changes, restoring a database under a running process, another uncooperative authority, and old runtimes require external fencing.

`recorded` is only database metadata, not physical verification. `pending_intent` is unresolved upload metadata, not completed or failed transfer. A complete listing says no other recorded metadata in that snapshot; it cannot rule out untracked temporary or orphan files and is not a receipt for any multipart request. No observation recovers or removes an intent or authorizes replay, commit, cleanup or delivery. Viewer must retain its ambiguous-upload hold until a separately agreed recovery protocol resolves lifecycle races.

## Isolated PR78 compatibility draft

This branch contains an exact shared schema validator for the revision bundle, and permits that bundle in TaskStore and held startup only when every expected SQL object and target trigger set match. Held startup still refuses any pending upload intent. The census `--allow-inventory-revision` option permits only the exact new bundle and initial `(1, 0)` row; it requires unchanged table content if already present and checks trigger sets. The flag is not wired into the cutover rehearsal. Schema installation and the HTTP endpoint remain disabled by default.

This resolves the source-level trigger incompatibility but does not qualify any production migration, restore, downgrade, or simultaneous authority. Exact schema validation assumes a trusted, exclusively owned SQLite database and no live restore or uncooperative schema writer. Cursor eviction/restart fail closed. No automatic replay or physical file verification is provided.
