# Paged source manifest candidate (inactive)

Version `ltds-paged-source-v1` is a synthetic metadata candidate only. It is not mounted, negotiated, authenticated, durable, broker-compatible, or authorized for processing. V1 remains unchanged. No live file content is fetched, and no transfer, retry, revocation or disk capacity is guaranteed.

A closure has exactly `version`, positive safe integer `objectCount`, positive safe integer `totalBytes`, positive `pageCount`, and ordered array `pages` of lowercase SHA-256 page digests. Each page has exactly `body` and `sha256`; its body has zero-based `index` and ordered `objects`. Each object has exactly `id`, `name`, `byteSize`, `sha256`, `kind`, `mediaType`; field rules follow reference-v1 slug, safe basename, positive safe integer, lowercase SHA-256, kind and bounded media type. IDs and case-folded basenames must be unique across the entire closure, and object counts and total bytes must match exactly.

The page digest is SHA-256 of UTF-8 bytes `ltds-paged-source-v1-page` followed by NUL, followed by reference-v1 canonical JSON for the page body. The closure pin is SHA-256 of UTF-8 `ltds-paged-source-v1-closure`, NUL, then reference-v1 canonical JSON of the complete closure. Canonical JSON uses sorted keys, no whitespace and UTF-8 as implemented by `reference_protocol.canonical_json`; cross-language canonical behavior needs agreed vectors before integration. Validation requires an independently authenticated externally pinned closure digest; trusting a digest supplied alongside mutable pages gives no authenticity. No identity, owner, environment, generation or lease is bound by this isolated format.

This prototype caps objects at 25,000, pages at 64, page members at 512, serialized page body at 256 KiB and total serialized page bodies at 8 MiB. Validation checks fields before serializing a page, rejects out-of-order/missing pages, wrong pins, altered hashes, duplicates, unsafe values, and returns detached object records in an ID-indexed dictionary. The caller must exclusively own the supplied decoded Python objects for the duration of validation; this is not a bounded network parser or a streaming page fetcher. No disk-backed index, crash recovery or memory/RSS limit is implemented.

The builder splits a page before either its 512-object or encoded-byte ceiling,
so long valid basenames do not force rejection merely because a fixed-size
page would be too large. It validates the entire input and computes bounded
page spans before copying or serializing page bodies. The existing page and
aggregate limits still apply; sufficiently long records may exceed them and
remain held. This does not change the separate Viewer frame producer.

A one-object test vector uses id `i`, name `a.jpg`, byteSize 1, SHA-256 `a` repeated 64, kind `image`, mediaType `image/jpeg`: page digest `c0f512a2a64fc24849b4cee33c5239773bc665f7b1085c4c0b7f0b94d77a05c2`; closure pin `0987a3830b10ca7c53a9ddc72138fa05a70fa0df96b5353fcbb039fcba6fa7a8`.

For a 16,832-object synthetic fixture, one local Python-traced run before adding the hash domains measured 2,980,046 page bytes, 1.39 seconds to construct and self-validate, 0.70 seconds to revalidate, and about 17.9 MB peak traced allocations. This is illustrative, excludes process RSS and runtime integration, and is not a production benchmark. Independent review and Viewer/broker agreement on immutable snapshots, identity, digest, bounded streaming, durable ledgers, request authentication, revocation, retry and storage budgets are required before use.

This format records only basenames and does not retain Viewer original relative paths, object roles, dataset identity, or GCP/auxiliary selection semantics. It must not replace the authoritative Viewer inventory. Any integration needs an authenticated link to that inventory and a pinned closure bound to coordinator authority, principal, environment, Viewer attempt, reservation, source version and revocation epoch; those links are not implemented here. The prototype accepts already decoded in-memory input and is not a bounded streaming transport parser. Builder checks all field, duplicate, total and per-page encoded limits before constructing page copies. A Node `canonicalize` cross-language test exercises Unicode, quotes/backslashes and a 512-to-513 page boundary; its external module is supplied only by the test harness.

Viewer coordination: keep this page format an envelope/index only, linked to the authenticated source inventory. Either a future negotiated page must bind exact dataset file ID, original path, role, inclusion/disposition, size, content hash, GCP substitution and custody, or it must carry an independently authenticated complete inventory digest and an unambiguous object-ID mapping to that inventory. Preserve nested paths; basename uniqueness is a separate materialization constraint. A hypothetical (not negotiated or validated) 16,832-record fixture including those fields serializes to 4,797,902 bytes across 33 pages, largest 145,944 bytes with short synthetic paths. This fits the candidate's current page/aggregate limits for this fixture only; long paths, richer GCP records and real records could differ. It does not prove Viewer mapping, custody, role or authorization correctness.

Paired/release-mode test requires `PAGED_MANIFEST_PAIRED_REQUIRED=1` and an absolute `NODE_JCS_MODULE` path. It checks the actual resolved package name `canonicalize`, version `2.1.0`, and entrypoint location inside the selected package before running; missing or incorrect dependencies fail rather than skip. This package-metadata check does not cryptographically establish package supply-chain integrity.

An expanded synthetic sizing fixture models 16,832 images with deeper client/survey/flight paths plus one generated GCP-control record with original/generated file IDs, CRS labels and 24 marker IDs: 16,833 hypothetical records, 33 pages, 5,825,442 bytes total and 177,176 bytes for the largest page. These are example values and shape, not the approved Viewer schema or bounds on arbitrary actual metadata. GCP record creation, custody and substitution are not implemented.

The paired cross-language vector also invokes the actual Viewer `canonicalBytes()` implementation copied byte-for-byte from Viewer commit `c92deb5ba143fd302bdf787ba832e0ac1bd0e2f0`, path `apps/viewer/server/referenceProtocol.js` (Git blob `f98e40b9db4a0f0544958e0c81961f83f99bd98b`, SHA-256 `030e820b876f4ca6500832a1cfe8b05ea8e7394fed7f3df2be4b070589ccfe20`). The test verifies that SHA-256 before executing the checked-in fixture. This tests canonical byte compatibility only; it does not imply Viewer understands the proposed pages or that this commit is deployed.
