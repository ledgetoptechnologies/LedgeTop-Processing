# Draft: preserve engine data at startup

The pinned NodeODX and NodeODM images remove old terminal tasks and stale uploads at startup and hourly. They also remove UUID-shaped directories missing from the restored task index. A malformed or partially restored index can cause stored task directories to be treated as orphans. These behaviors are independent of the host cleanup cron and of Viewer acceptance.

The two draft Dockerfiles build on the exact installed upstream image digests. The build-time patcher verifies the original and patched `TaskManager.js` SHA-256 before completing. It refuses unknown sources. It retains each image's original effective Docker `USER` and entrypoint; this does not change a running container or its mounts, credentials, command, or restart policy.

The draft validates a bounded index snapshot and task-directory identities before deserialization, deserializes that snapshot one task at a time, and checks identity again before the progress listener and dispatch. It fails closed for missing, malformed, inconsistent, duplicate or noncanonical identifiers and for queued, running or unknown statuses. An empty new data directory is allowed. It does not automatically delete orphan directories, old terminal jobs or stale uploads at startup or on the hourly timer. Explicit engine API removal is unchanged; no Viewer-acknowledged cleanup is provided here.

## Qualification and limits

`tests/nodeodm_startup_preservation.js` runs the image's actual patched TaskManager in disposable containers. The 19 named cases cover fresh stores, malformed and incomplete indexes, path-like and duplicate identifiers, async restore failure, a synthetic restored old terminal task, running/queued holds, a changed index and a new directory during asynchronous restore, and the hourly cleanup calls. Two additional nonempty cases enable normal postprocessing option discovery through a controlled asynchronous interface; one causes an actual asynchronous directory-read failure and checks that the next task is never started. Tests must run with **only synthetic tmpfs** at `/var/www/data` and `/var/www/tmp`, no host-data mounts or live engine ports. These tests use mocked logging, scheduler and option discovery; they do not run the real option-discovery subprocess.

This is not production-ready. Snapshot identity checks do not exclude writers after the final check, and an administrator or Docker user can bypass them; independent writer fencing is required. A queued or running task blocks startup and needs a separate recovery procedure. Restoration is serialized but has no deadline: a stuck upstream option-discovery subprocess can still hold startup. The unchanged task-index dump is not made atomic, and power loss is not tested. Strict lowercase UUIDs and the 64 MiB index/100,002 directory-entry limits require evaluation against existing databases. Long-term disk accounting, safe authenticated acknowledgement-based cleanup, source ingestion/recovery, and target-specific backup/rollback remain separate requirements. Do not replace, restart, update or otherwise alter a live engine from this draft.
