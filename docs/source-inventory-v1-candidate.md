# Provisional Viewer source inventory v1

This pure, inactive proposal is not connected to admission, transfer, Viewer,
or cleanup. The contract and Viewer signer have not been agreed. It hashes
RFC 8785 JCS bytes prefixed with ASCII `ltds-source-inventory-v1` and NUL.
It uses the separately pinned optional `rfc8785` candidate dependency; no
production image or runtime is changed.

The isolated successor also accepts a separately domain-versioned v2 wire
form with an explicit `substitutions` array for one original raw GCP file
replaced or excluded when an attempt-generated snapshot is sent. Its source
ID/path/hash/original role and generated attempt ID are explicit; the source
stays in retained custody. This does not change the v1 interpretation.

The closed root has `protocol`, `schemaVersion`, `dataset`, `binding`,
`processing`, `retained`, and `generated`. Dataset contains `id` and
`manifestSha256`; binding contains `viewerTaskId`, `viewerAttemptId`, and the
server-owned `pipelineDigest`. Each original file descriptor contains exact
`datasetFileId`, `relativePath`, `byteSize`, `sha256`, `processingRole`, and
`contentType`. Processing and retained lists are disjoint and each sorted by
dataset file ID; together they must equal an independently authenticated,
sorted authoritative dataset file mapping on ID/path/size/hash/content type.
Viewer remains custodian of the original files in both lists. The proposed
resolved role vocabulary is `image` and `provider_input` for processing,
`gcp_source` and `administrative` for retained-only inputs; unresolved `auto`
is held. Viewer agreement on vocabulary and MIME representation is pending.
An independently authenticated trusted attempt selection binds every file's
resolved role and processing/retained disposition, task/attempt/pipeline, and
an explicit `gcpRequired` boolean. A missing required GCP or an unexpected GCP
is held. The candidate admits up to 20,000 original dataset sources, at most
10,000 of which are non-photo sources. The reference-v1 processing cap is
10,000 engine objects **including generated GCP**: 10,000 photos plus GCP are
held until that engine protocol limit changes. The 12 MiB raw metadata and
structure bounds can independently hold a large inventory; they are not a
promise that every possible 20,000-source metadata set fits.

The caller must independently authenticate the authoritative dataset mapping
and bind it to the dataset ID and manifest SHA. This candidate compares the
mapping and claimed SHA, but does not recompute or authenticate Viewer's
manifest: that algorithm, trusted loader, revision/writer fence and complete
mapping must be agreed and verified before it can establish completeness.
When the authoritative mapping's contentType is null, the separately trusted
indexed mimeType supplies the inventory content type. Non-null contentType
is retained; absent or invalid fallback values hold.
The proposal preserves original Unicode code points and case exactly; no NFC,
case folding, or path flattening occurs in the inventory. It rejects exact path
or ID duplicates, traversal and unsafe separators. Different directories can
contain the same basename, and case or Unicode-normalization variants remain
distinct. A target filesystem must preflight its own collision/representation
rules before writing. The separate `reference_v1_names` preflight rejects
non-ASCII/unrepresentable basenames and ASCII case-insensitive collisions;
it does not provide a safe copy or file materializer.

`generated` is empty or has one attempt-specific GCP descriptor containing
`snapshotId` (exact Viewer attempt ID), `byteSize`, `sha256`, sorted unique
`sourceGcpDatasetFileIds`, sorted unique `imageDatasetFileIds`, and positive
`correspondenceCount`. Sources must resolve to retained `gcp_source` files;
image IDs must resolve to processing `image` files. The generated bytes are
bounded and their exact length and hash checked. The original Emlid CSV stays
retained. Independently supplied trusted snapshot metadata and correspondence
rows must match the descriptor, count and distinct source/image IDs. The
candidate now parses `EPSG:4326` lines and checks ordered coordinates, pixels
and exact image basenames against supplied immutable correspondence rows,
including Viewer's binary64/toFixed(8) rounding. It rejects duplicate or
ambiguous image basenames, point/image pairs and identical physical rows.
Coordinate/pixel bounds are conservative proposed limits, not Viewer policy.
It does **not** authenticate the supplied rows or establish their immutability;
the actual Viewer snapshot and database join need agreement and implementation.
Binding a digest is not an upload,
durable receipt, result or cleanup authorization.
The pure validator returns a held status even when structural checks pass:
GCP evidence authority/immutability and the underlying source authority/manifest
have not been authenticated by this candidate.

The synthetic tests use actual Node `canonicalize@2.1.0` and Python
`rfc8785==0.1.4`, exercising exact non-ASCII spelling, case/basename behavior,
source completeness and generated byte mismatch. They do not run the actual
Viewer sender or establish cross-service interoperability.
Additional synthetic tests call the actual Viewer `gcpOdm.js` from commit
`793aa66ba0c515287a8cfe1eebc3b763b01d2cef` (Git blob
`81dc6b7bd20cc3505cd3a33e8222ba5acb9e845c`) and compare its output with the
semantic checker. Viewer currently snapshots bytes/count at attempt creation,
at commit `793aa66` the source implementation did not freeze corresponding
rows. Viewer migration 44 now proposes per-attempt immutable evidence with full
correspondence, point and set IDs, raw source ID/hash/path, image ID/path and
nullable dimensions. This candidate matches that row shape, validates identity,
source mapping, original spelling, dimensions and pixel bounds, and preserves
the supplied capture order. It has no authenticated Viewer loader; reading
subsequently mutable marks as proof remains unsafe. Exact trusted evidence
provenance and numeric bounds must be agreed before any integration.

Evidence bytes are independently bounded to 12 MiB and 10,000 correspondence
objects with structural preflight before JSON allocation. Viewer currently
permits 64 MiB and 100,000 rows, so this candidate holds larger evidence and is
not capacity-compatible. Agreement on an authenticated, byte/hash-bound,
incrementally parsed evidence stream, row/depth/string limits, per-process
memory budget, backpressure and durable spool is required before adopting the
larger ceiling; increasing a full-tree parser's byte cap is not sufficient.
The candidate deliberately holds some inputs the current Viewer generator can
emit: colliding ASCII case-insensitive basenames, non-ASCII basenames, duplicate
point/image or identical rendered rows, and coordinates or pixels outside its
conservative bounds. Viewer itself only rejects empty or whitespace-containing
basenames and non-finite numbers in this generator. These stricter checks are
provisional and do not imply that Viewer has adopted them. Tests compare actual
Viewer output at negative rounding boundaries, signed zero, 1e-8, multiple
ordered rows and duplicate-basename cases; they do not establish the source
rows' authenticity or a complete cross-service protocol.
