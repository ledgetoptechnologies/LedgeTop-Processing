# Draft enrolled legacy-fence enforcement

This isolated branch extends PR82; it is not deployed. An explicit offline enrollment takes both the candidate and legacy state locks and stores a marker in the stopped candidate database. The marker binds the exact legacy lock device/inode and matching coordinator authority. The default coordinator entrypoint detects the marker and acquires the original lock before opening its queue or listeners; a wrong/missing lock, authority mismatch or malformed marker holds startup. When `PROCESSING_LEGACY_FENCE_REQUIRED=1`, a missing marker also holds startup. Marker-enrolled state continues to require the fence even if the flag is omitted. The lock remains owned through queue lifetime and is released only as the queue closes after service drain.

The optional cutover spec `--legacy-fence-volume` accepts only the exact original named volume identified in the inspected old container, distinct from candidate and authority-lease volumes; it adds a read-only `/legacy-state` mount and the required flag. This specification does not enroll the marker, attest that the old inspection still represents the actual host, disable an updater or validate a real cutover. The existing `ops/update_reference_coordinator.py` constructs its own restart-unless-stopped container and does not yet carry the new mount and flag. Documented cluster notes say Docker is enabled at boot and the coordinator uses `unless-stopped`; the actual currently installed systemd and updater configuration was not inspected or verified for this draft.

This mechanism relies on a trusted supervisor and unchanged original and candidate files/volumes, requires all legacy launchers to use the exact fenced state lock, and cannot prevent an old process from using an unfenced state copy, a privileged actor from changing configuration or state, or a restored state from bypassing a missing marker if the required flag is also removed. Device/inode values can change across host reboot or storage remount: the conservative result is a startup hold, not automatic recovery. A durable rollout and rollback procedure, census schema allowance, updater integration and exclusion, interrupted-enrollment recovery, actual host/daemon restart tests, and Viewer processing validation remain required. Never stack PR82's wrapper entrypoint over this enrolled app: both would attempt to lock the same inode and startup will hold.
